The route / in order

Five decisions, one clearer question

Each phase changed the experiment because the previous metric exposed a different failure mode.

01
Starting pointone-shot

Ask for the completed grid

The first trainer optimized for a full Sudoku solution. It proved QLoRA could run on the local GPU, but a completed grid hid the intermediate reasoning and made it hard to tell whether an answer was derived or guessed.

92.05%teacher-forced token accuracy
abandonedtoo broad to verify
02
Narrow the taskdeduction v1

Make one deduction a testable object

The target became structured JSON: technique, witness, placements, and eliminations. An independent validator checks the candidate state, witness, and state transition. This separated formatting from logical soundness.

100%JSON parse on the benchmark

03
Prompt ablationv2 rulebook

Add the rules, and watch the interface break

A formal rulebook and coordinate specification were added at evaluation time. On the existing v1-trained adapter, the longer prompt caused schema drift instead of transferring usable rule knowledge. The result argued for matched retraining, not more prompt text.

04
Representation warm-upv2 → candidate-lite

Teach the model to see the board first

Before asking for deductions, train the visible operations underneath them: cells, coordinates, units, peers, candidate locations, and naked-single scans. The first full epoch reached 95.52% exact; a targeted candidate-location continuation lifted it to 98.44% while preserving the easy tasks.

The representation result is a foundation, not a claim of Sudoku reasoning. The next run should use the same labeled grid format, a compact v3 rulebook during training and evaluation, and generated soundness as the primary signal.

Reasoning behind the choices

The decision log

These are the conclusions the evidence supports now, with the assumption behind each one kept visible.

A

Stop using token accuracy as the finish line

Teacher-forced accuracy measures whether the next expected token is familiar. It does not test whether a generated witness identifies a legal deduction.

Evidence: 91.10% validation token accuracy beside 0.457% held-out soundness.
B

Build the representation layer before the reasoning layer

A deduction depends on finding cells, candidates, peers, and units. Make those operations independently measurable so a failure can be localized instead of hidden inside one final score.

Evidence: candidate-lite reached 98.44% exact and 100% on core lookup tasks.
C

Use targeted data where the heatmap is cold

The first representation run was already strong on simple lookups. Add more balanced, non-empty box and multi-cell queries, while replaying the old tasks to protect what already works.

Evidence: candidate-location exact improved from 82.34% to 94.02%.
The next honest test

Prove the bridge, not just the parts.

The project has a validated data pipeline, working adapters, and a useful representation model. The next result should answer whether those capabilities transfer to a sound deduction when the prompt, format, and training objective are aligned.

  • Evaluate the unfine-tuned base model on the same frozen benchmark.
  • Retrain with the compact v3 rulebook, not an evaluation-only prompt change.
  • Start with singles and pairs before triples, quads, and fish.
  • Use generated soundness as the primary validation signal.

Measurement rule

A prediction counts as progress only when an independent validator accepts its witness and state transition. A parseable answer is a prerequisite, not a success condition.
